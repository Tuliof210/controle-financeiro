# Learnings — Pocket Squad

Durable, one-line rules. Appended by /ps:publish after each merge; read by
/ps:story during refinement. A rule must change future behavior — otherwise
delete it. Cap: 30 rules; when adding past the cap, delete the weakest one.

Format: `- [scope] imperative rule (added YYYY-MM-DD)`

---

- [worktree] After EnterWorktree, immediately rename the branch to ps/<story-slug>/<task-slug> — it auto-generates worktree-ps+<slug>+<task> (/ → +), breaking the ps/<slug>/* convention /ps:load's PR cross-check relies on (added 2026-07-21)
- [biome] Run `npx biome explain <rule>` before trusting any rule snippet — create-next-app's pinned Biome version can predate a rule entirely (noExcessiveLinesPerFile needs >=2.3.12), and a rule's group (style/complexity/nursery) shifts across releases (added 2026-07-21)
- [publish] `gh pr merge --delete-branch` routinely fails to delete the branch (local and/or remote) whenever it's checked out in any worktree — expected here, since this workflow leaves each task's worktree in place until an explicit cleanup step. Treat the failure as normal: confirm the merge itself succeeded via `gh pr view --json state,mergedAt`, then `git worktree remove` the task's worktree, `git branch -D` the local branch, and `git push origin --delete` the remote one — verify the remote is actually gone with `git ls-remote --heads`, since a failed local deletion seems to abort before remote deletion runs (added 2026-07-21)
- [worktree] /ps:story's story/task `.md` files sit uncommitted on the main checkout; `git worktree`/EnterWorktree branches from committed history, so /ps:run must copy them into the task's worktree, commit them there, AND delete the main checkout's now-stale untracked copy — otherwise the task's "check the box" step has nothing to edit, and the leftover copy trips /ps:publish's dirty-checkout preflight later (added 2026-07-21)
- [publish] `gh pr merge` itself (not just its `--delete-branch` flag) can fail with `fatal: 'main' is already used by worktree` when run while cwd is inside another worktree of the same repo — ExitWorktree back to the main checkout before calling `gh pr merge`, not only before the later branch-cleanup step (added 2026-07-21)
- [browser-preview] `preview_start`'s `{name}` launcher always runs from the main checkout's directory, never from a task's EnterWorktree cwd — to visually verify a worktree-isolated change, start the dev server manually from inside the worktree on a spare port, then `preview_start` with `{url: "http://localhost:<port>"}` (added 2026-07-21)
- [storybook] A Foundations-only Storybook (MDX `<Meta>` docs, no CSF stories) breaks `@storybook/addon-themes`'s theme decorators — they only run inside a story's render (a `useEffect` in the returned decorator function), so the toolbar updates Storybook's internal globals/URL but never writes `data-theme` to the DOM for a docs-only page. Fix: wire the toggle directly via `globalTypes`/`initialGlobals` + `addons.getChannel().on("updateGlobals", ...)` in `preview.ts` instead (drop the addon) — works for both docs-only pages and future CSF stories alike. Revisit once real component stories land (added 2026-07-21)
- [css] Never mix a `:hover` (or other pseudo-class) CSS rule with an inline `style={{...}}` on the same property on the same element — the inline style always wins regardless of the pseudo-class matching, so the hover state silently never applies. The property that needs to change on `:hover` (or focus/active) must live in an actual stylesheet/class rule, not inline; this bit a "hover to preview" demo where the box never visibly changed color despite `:hover` correctly matching and the transition firing (added 2026-07-21)
- [worktree] The auto-mode classifier blocks `rm -rf` on the main checkout even for a stale untracked copy that's safe to discard (e.g. the leftover from the /ps:story-files-copy step above) — use `mv` to relocate it (scratchpad, or anywhere outside the repo) instead of deleting; that's reversible and isn't blocked (added 2026-07-21)
- [run] Before warning the owner that a task's dependency isn't checked in `story.md`, `git pull` and re-check the dependency PR's state first — it can merge out-of-band between conversation turns (owner, another session) without the local checkout or loaded context knowing, silently resolving what looked like a blocker (added 2026-07-21)
- [worktree] `node_modules` is never shared across git worktrees — a dependency installed in one task's worktree (e.g. `npm install lucide-react`) only lands in that worktree's `package.json`/lockfile once its PR merges, but the *next* task's worktree branches from that updated main with the manifest correct and `node_modules` still empty of it. `npm run lint`/`test` can still pass by resolving pre-existing packages from the main checkout's `node_modules` (Node's parent-directory walk-up, since worktrees live nested under `.claude/worktrees/`), masking the gap until `next build` actually tries to bundle the new import. Run `npm install` at the start of any task whose "Depends on" installed a package (added 2026-07-22)
- [review] Before a PR body claims a specific artifact was added exactly as the task file prescribed (a `ponytail:` comment, a particular pattern), grep the actual diff to confirm — a prior task dropped a prescribed comment during implementation but the PR description still claimed it was there, caught only by a fresh-eyes reviewer diffing the claim against the code (added 2026-07-22)
- [worktree] `EnterWorktree` refuses to run from inside an `Agent`-tool-spawned subagent (cwd-override restriction) — when dispatching parallel `/ps:run` tasks via `Agent`, have each subagent go straight to `git worktree add -b ps/<slug>/<task> <path>` instead of attempting `EnterWorktree` first; the tool only works from the top-level session, not a spawned subagent (added 2026-07-22)
- [publish] After a task's PR merges, `git checkout <base>` + `git pull --rebase` in the main checkout can abort with `error: The following untracked working tree files would be overwritten by merge` if the checkout still holds the pre-merge untracked story/task `.md` copy (see the `/ps:story`-files rule above) — the incoming commit now tracks those exact paths. `mv` the untracked copy to scratchpad (never `rm`, per the rule above) and retry; safe since the merged commit already carries the authoritative content (added 2026-07-22)
- [publish] Commit the story/task `.md` files to `main` BEFORE spawning parallel `/ps:run` worktrees — this avoids the add/add `story.md` conflict entirely (otherwise each worktree independently commits an identical copy, and the first merge flips every other PR to `CONFLICTING`). One residual remains even after committing first: each PR ticks a *different* task's checkbox, but the boxes sit on adjacent lines, so git's 3-way merge (3-line context) still flags `story.md` `CONFLICTING` once the first PR merges. Resolve per still-open PR from its worktree: `git fetch origin main && git merge origin/main`, keep ALL already-merged boxes checked plus this branch's own, `git commit --no-edit`, push — `mergeable` settles to `MERGEABLE` a few seconds later. Merging the PRs one at a time (not all at once) keeps each conflict small (added 2026-07-23)
- [tooling] The harness's persistent Bash shell does not reliably keep a `cd`'d directory across separate tool calls — it can silently revert to a previously-visited worktree between two calls in the same turn (observed twice while publishing three sequential PRs), even though the tool description says cwd persists. Symptom: `git checkout <branch>` / `gh pr merge` fails with `fatal: '<branch>' is already used by worktree at <main-checkout>` right after a prior call's `pwd` confirmed you were already back in the main checkout. Don't trust a `pwd`/`cd` from an earlier call — re-`cd` (or `git -C <path>`) and verify `pwd`/`git branch --show-current` in the SAME call as any cwd-sensitive git operation, especially right before `gh pr merge` (added 2026-07-22)
- [architecture] This project's testing convention colocates tests only with `service.ts`, never `route.ts` — so `route.ts`-only logic (request-body parsing guards, Prisma-error-to-HTTP-status mapping) has zero automated coverage; only a manual smoke test or a review catches it. Confirmed in practice: a Route Handler task shipped clean `service.test.ts` coverage while both a delete-on-missing-id crash (uncaught `P2025`) and a malformed-JSON-body crash (uncaught `SyntaxError` from `request.json()`, thrown before Zod ever runs) lived entirely in `route.ts`, invisible to `npm run test`. When writing or reviewing a Route Handler task, explicitly require not-found-delete and malformed/empty-body as manual-smoke-test cases, not just the happy/duplicate/validation paths (added 2026-07-22)
- [architecture] `MonthPicker` (`src/components/MonthPicker`) self-seeds an `onChange(currentYYYYMM())` the instant it mounts/renders with `value=null`, indistinguishable at the call site from a real user pick — any consumer binding raw setState to it needs a separate "touched"/"loaded" flag before treating the bound value as save-worthy, or Save can silently persist a default no one chose. Bit `RangeSection` twice in the same PR before the guard was added (added 2026-07-22)
- [architecture] `src/lib/api.ts`'s `request()` (and `apiGet`/`apiPost`/`apiPut`/`apiDelete`) never rejects — every failure (bad response body, thrown `fetch`, non-OK status) resolves to `{ error }`. Any `.then()`/`await` caller that doesn't check `result.error` before acting on `result.data` treats a failed load as success; this silently defeated a "wait for load before enabling Save" guard until the check was added explicitly (added 2026-07-22)
- [browser-preview] The `computer` tool's `key` action (End, Backspace, etc.) doesn't reliably register on focused text inputs in this environment — repeated Backspace presses left a `MoneyInput`'s value completely unchanged. `triple_click` (select-all) + `type` is the reliable way to reset/replace field content; verify a click actually fired via `read_network_requests` (a "left_click succeeded" response doesn't guarantee the handler ran) rather than trusting the tool's own success message, and fall back to `javascript_tool`'s `element.click()` when a ref-based click produces no network activity (added 2026-07-22)
- [browser-preview] To reproduce an async load-failure bug live, patch `window.fetch` via `javascript_tool` then force the component to remount without a full page load — a full `navigate`/reload silently resets the patch back to native `fetch`, and even a client-side `<Link>` click can trigger a full reload in this tool. Editing the component's file with a hook-signature-changing edit (e.g. adding a throwaway `useState` call) reliably forces React Fast Refresh to remount it in place, re-running effects against the patched `fetch`; a comment-only edit does not force the remount (added 2026-07-22)
- [review] A PR description's "Decisions" prose can go stale mid-review-cycle when a later fix changes something the description already described as fact (e.g. "X duplicates Y" became false once X was refactored to share Y). Before merging, diff the description's specific claims (line counts, "duplicates Z", "no test needed because...") against the current code, not just append new fixes to the bottom (added 2026-07-22)
- [architecture] The Prisma CLI (`prisma.config.ts`) and the runtime client (`src/infra/db/client.ts`) resolve `DATABASE_URL` independently — if only the runtime has a `?? "file:./dev.db"` fallback and the CLI doesn't, `prisma migrate deploy` aborts ("datasource.url property is required") while the app silently connects to an empty, table-less DB, so every query 500s ("no such table", surfaced to the UI as "Erro inesperado"). Keep both fallbacks aligned, expose a `db:setup` (`prisma migrate deploy`) npm script, and run `npm run db:setup` in EVERY fresh worktree before hitting the API — the SQLite file is gitignored and not shared across worktrees, and node_modules parent-walk-up doesn't cover the DB file (added 2026-07-23)
- [browser-preview] React state updates are async, so reading DOM/`dialog.open` state in the SAME `javascript_tool` call right after a synthetic `.click()` sees the stale pre-render value (a just-opened modal reads `open:false`; a just-closed one reads `open:true`) — always check the result in a SEPARATE call so React has re-rendered and effects have run. Combined with the missed-`computer`-click gotcha (a ref click can land on nothing and fire no handler), this masquerades as a broken handler when the code is fine; confirm via a fresh state read + `read_network_requests`, never the click tool's own success message (added 2026-07-23)
- [architecture] Adding a new Prisma relation FK defaults to `ON DELETE RESTRICT` (Prisma's implicit default) — this can silently break an EXISTING sibling delete endpoint that doesn't handle the resulting `P2003` error code. Confirmed in practice: adding `Recurrence.owner → Person` made `DELETE /api/people` (untouched, already-shipped code) throw an uncaught `PrismaClientKnownRequestError` → HTTP 500 with no JSON body, breaking the `{error:{message,code}}` envelope contract, whenever the person still has a recurrence. When adding a new relation FROM entity A TO entity B, audit every existing delete handler on B for `P2003` handling — don't assume only the new entity's own routes need error-code coverage (added 2026-07-23)
- [architecture] A domain entity field typed as a literal union (e.g. `type: "income" | "expense"`) has no Prisma enum behind it in this codebase (project convention: no Prisma enums — `type String` + `z.enum` at the route boundary) — so the generated Prisma client types it as plain `string`, and a repository method returning the raw Prisma row fails `tsc` against the narrower domain type. Person/Goal never hit this since neither has a literal-union field. Fix is an explicit `as Promise<Entity>` cast on the repository method (with a `ponytail:` comment noting Zod already guards the value at the write boundary) — expect this on every future entity with a literal-union field, not just this one (added 2026-07-23)
- [architecture] Persisted client state (`localStorage`) that stores a REFERENCE to another mutable entity's id — not a fixed enum like `ThemeToggle`'s `"light"|"dark"` — goes stale forever if the referenced entity is later deleted, unless something reconciles it once that entity's list loads. Confirmed in `ProfileProvider`: deleting the person behind the active `profile` left the derived `label` correctly falling back to "Família" (so the UI looked fine), but the raw `profile` id and `localStorage["profile"]` kept the dangling id indefinitely — invisible today, but any future consumer that filters by comparing the raw id (not the label) would silently render empty instead of falling back to "show all". Fix: once the referenced list has actually finished loading (guard on a loaded flag, not just a non-empty check, or a fresh unmatched pick gets wrongly reset), add an effect that resets to the safe default when the stored id no longer matches anything (added 2026-07-23)
- [prisma/migrate] For a Prisma+SQLite schema change that must PRESERVE existing data (e.g. splitting `rangeStart`/`rangeEnd` into a `RecurrenceMonth` child table), generate with `npx prisma migrate dev --name X --create-only` then hand-edit the SQL: a column drop is a table REBUILD (CREATE new_ / INSERT…SELECT / DROP / RENAME), so put the data-backfill INSERT AFTER the new child table's `CREATE TABLE` but BEFORE that rebuild block — it must read the old columns while they still exist. YYYYMM is monotonic as an int, so a recursive CTE expands a range month-by-month (`CASE WHEN m%100=12 THEN (m/100+1)*100+1 ELSE m+1 END`, `WHERE m<endM`); use `lower(hex(randomblob(16)))` for raw-insert ids since `@default(cuid())` only fires for Prisma-issued writes. Neither `migrate dev --create-only` nor `migrate deploy` regenerates the client — run `npx prisma generate` after any schema edit or the build/types stay stale. Verify by seeding old-schema rows in a throwaway db and applying the migration (added 2026-07-24)
- [biome/react] Biome's react-recommended `noArrayIndexKey` fails lint on `key={index}` in a `.map`. For a dynamic list of rows without natural ids (user adds/removes intervals), give each row a stable key from a monotonic `useRef` counter in the state hook (`{...it, key: nextKey.current++}`), never the index — index keys also mis-associate controlled rows across a middle removal. Extracting that keyed-row state into its own `*.hook.ts` sibling doubles as the fix when a form `hook.ts` outgrows the 100-line cap (added 2026-07-24)
- [react/browser-preview] A controlled input that reformats its value on EVERY keystroke (e.g. `MoneyInput`, integer-cents re-derived via `formatCents`/`digitsToCents`) needs THREE caret handlers to stop a mid-field / left-of-comma insert from shifting the value by a decimal place (R$ 6,00 → R$ 600,00): `onFocus` → caret-to-end; a post-reformat `useLayoutEffect` keyed on the formatted string (reference the string itself, e.g. `display.length`, inside the effect body — reading the equivalent off the ref instead makes Biome's `useExhaustiveDependencies` flag the dep as unnecessary); AND `onSelect` that snaps a *collapsed* caret to the end but leaves a range selection (`selectionStart !== selectionEnd`) intact, so select-all-to-replace still works and there's no re-fire loop. The effect alone fires one keystroke too late — the `onSelect` closes that gap. When e2e-driving such a field, send ONE key per `computer.type` call and read the result in a SEPARATE call: a multi-char string ("600") races the controlled re-render and compounds intermediate digits ("6000,00"), a machine-speed artifact real human cadence never hits (added 2026-07-24)
