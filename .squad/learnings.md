# Learnings — Pocket Squad

Durable, one-line rules. Appended by /ps:publish after each merge; read by
/ps:story during refinement. A rule must change future behavior — otherwise
delete it. Cap: 30 rules; when adding past the cap, delete the weakest one.

Format: `- [scope] imperative rule (added YYYY-MM-DD)`

---

- [biome] Run `npx biome explain <rule>` before trusting any rule snippet — the pinned Biome version can predate a rule entirely (noExcessiveLinesPerFile needs >=2.3.12), a rule's group (style/complexity/nursery) shifts across releases, AND its default severity may not be `error`: both noExcessiveLinesPerFile and noExcessiveLinesPerFunction are `info` at `level: "on"`, so the 100-line cap does NOT fail `npm run lint` despite ARCHITECTURE.md calling it "enforced by Biome". It is a review responsibility; the lint run only reports it as one of the `Found N infos` (added 2026-07-21, revised 2026-07-25)
- [publish] `gh pr merge --delete-branch` routinely fails to delete the branch (local and/or remote) whenever it's checked out in any worktree — expected here, since this workflow leaves each task's worktree in place until an explicit cleanup step. Treat the failure as normal: confirm the merge itself succeeded via `gh pr view --json state,mergedAt`, then `git worktree remove` the task's worktree, `git branch -D` the local branch, and `git push origin --delete` the remote one — verify the remote is actually gone with `git ls-remote --heads`, since a failed local deletion seems to abort before remote deletion runs. This is not hypothetical drift: by PR #48 thirteen merged `ps/*` branches had accumulated on the remote from earlier stories, every one of them a publish where the remote delete was skipped after the local one failed. Run `git ls-remote --heads origin 'ps/*'` at the END of every publish, not just after the failing command (added 2026-07-21, extended 2026-07-27)
- [browser-preview] `preview_start`'s `{name}` launcher always runs from the main checkout's directory, never from a task worktree's cwd — to visually verify a worktree-isolated change, start the dev server manually from inside the worktree on a spare port, then `preview_start` with `{url: "http://localhost:<port>"}` (added 2026-07-21)
- [worktree] `node_modules` is never shared across git worktrees — a dependency installed in one task's worktree (e.g. `npm install lucide-react`) only lands in that worktree's `package.json`/lockfile once its PR merges, but the *next* task's worktree branches from that updated main with the manifest correct and `node_modules` still empty of it. `npm run lint`/`test` can still pass by resolving pre-existing packages from the main checkout's `node_modules` (Node's parent-directory walk-up, since worktrees live nested under `.claude/worktrees/`), masking the gap until `next build` actually tries to bundle the new import. Run `npm install` at the start of any task whose "Depends on" installed a package (added 2026-07-22)
- [review] Every specific claim in a PR body is a liability until diffed against the code: an artifact the task file prescribed (a `ponytail:` comment, a pattern), a line count, a test count, "X duplicates Y", "no test needed because…". All three failure modes have happened here — a prescribed comment dropped during implementation, a "duplicates Z" claim left standing after the refactor that made it false, and test counts restated in a follow-up COMMENT while the body itself stayed stale through two review rounds. Re-read the body top to bottom against the final diff before every push, not just append the new fix to the bottom (added 2026-07-22, merged 2026-07-25)
- [publish] Commit the story/task `.md` files to `main` BEFORE spawning parallel `/ps:run` worktrees — this avoids the add/add `story.md` conflict entirely (otherwise each worktree independently commits an identical copy, and the first merge flips every other PR to `CONFLICTING`). A residual conflict is possible but NOT guaranteed: each PR ticks a *different* task's checkbox, and git's 3-way merge flags `story.md` `CONFLICTING` only when the boxes are close enough to share diff context — two lines apart merged cleanly on 2026-07-25, one line apart did not on 2026-07-23. Check `mergeable` after each merge instead of assuming either outcome. Resolve per still-open PR from its worktree: `git fetch origin main && git merge origin/main`, keep ALL already-merged boxes checked plus this branch's own, `git commit --no-edit`, push — `mergeable` settles to `MERGEABLE` a few seconds later. Merging the PRs one at a time (not all at once) keeps each conflict small (added 2026-07-23)
- [tooling] The harness's persistent Bash shell does not reliably keep a `cd`'d directory across separate tool calls — it can silently revert to a previously-visited worktree between two calls in the same turn (observed twice while publishing three sequential PRs), even though the tool description says cwd persists. Symptom: `git checkout <branch>` / `gh pr merge` fails with `fatal: '<branch>' is already used by worktree at <main-checkout>` right after a prior call's `pwd` confirmed you were already back in the main checkout. Don't trust a `pwd`/`cd` from an earlier call — re-`cd` (or `git -C <path>`) and verify `pwd`/`git branch --show-current` in the SAME call as any cwd-sensitive git operation, especially right before `gh pr merge` (added 2026-07-22)
- [architecture] This project's testing convention colocates tests only with `service.ts`, never `route.ts` — so `route.ts`-only logic (request-body parsing guards, Prisma-error-to-HTTP-status mapping) has zero automated coverage; only a manual smoke test or a review catches it. Confirmed in practice: a Route Handler task shipped clean `service.test.ts` coverage while both a delete-on-missing-id crash (uncaught `P2025`) and a malformed-JSON-body crash (uncaught `SyntaxError` from `request.json()`, thrown before Zod ever runs) lived entirely in `route.ts`, invisible to `npm run test`. When writing or reviewing a Route Handler task, explicitly require not-found-delete and malformed/empty-body as manual-smoke-test cases, not just the happy/duplicate/validation paths (added 2026-07-22)
- [architecture] `MonthPicker` (`src/components/MonthPicker`) self-seeds an `onChange(currentYYYYMM())` the instant it mounts/renders with `value=null`, indistinguishable at the call site from a real user pick — any consumer binding raw setState to it needs a separate "touched"/"loaded" flag before treating the bound value as save-worthy, or Save can silently persist a default no one chose. Bit `RangeSection` twice in the same PR before the guard was added (added 2026-07-22)
- [architecture] `src/lib/api.ts`'s `request()` (and `apiGet`/`apiPost`/`apiPut`/`apiDelete`) never rejects — every failure (bad response body, thrown `fetch`, non-OK status) resolves to `{ error }`. Any `.then()`/`await` caller that doesn't check `result.error` before acting on `result.data` treats a failed load as success; this silently defeated a "wait for load before enabling Save" guard until the check was added explicitly. Second trap in the same helper: it returns `{ data: body?.data }` for ANY 2xx, so a 200 with no `data` key (or a 204) resolves to `{ data: undefined, error: undefined }` — neither branch. `?? []` degrades safely, but a component using `null` as its LOADING sentinel and writing `?? null` strands itself on the spinner forever with nothing in flight; guard `if (result.error || !result.data)` instead (added 2026-07-22, extended 2026-07-25)
- [browser-preview] The `computer` tool's `key` action (End, Backspace, etc.) doesn't reliably register on focused text inputs in this environment — repeated Backspace presses left a `MoneyInput`'s value completely unchanged. `triple_click` (select-all) + `type` is the reliable way to reset/replace field content; verify a click actually fired via `read_network_requests` (a "left_click succeeded" response doesn't guarantee the handler ran) rather than trusting the tool's own success message, and fall back to `javascript_tool`'s `element.click()` when a ref-based click produces no network activity (added 2026-07-22)
- [design-system] `src/styles/tokens.test.ts` is a hardcoded allow-list, not an enumeration — adding a token to `_tokens.scss` and stopping there leaves rule 6 unenforced for it, silently. Append the name to `REQUIRED_SEMANTIC_COLORS` too. Two gaps to know before trusting a green run: (a) it **concatenates** the `[data-theme="dark"]` and `:root:not([data-theme="light"])` buckets, so a token declared in only ONE dark block passes — verified by mutation on PR #48, and that is exactly the case that breaks OS-dark users who never touched the toggle, so declare in all three blocks by hand (`--elevation-overlay` is the placement precedent); (b) elevation is not covered at all, and its real gate is `_theme.scss`'s `@mixin elevation` — an `@if/@else if` chain ending in `@error`, so a new elevation token needs the mixin extended or `@include t.elevation(x)` fails the Sass compile. When nothing consumes a new token yet, `npm run build` proves nothing — compile-probe with `npx sass --no-source-map --load-path=src/styles <throwaway>.scss` (added 2026-07-27)
- [architecture] The Prisma CLI (`prisma.config.ts`) and the runtime client (`src/infra/db/client.ts`) resolve `DATABASE_URL` independently — if only the runtime has a `?? "file:./dev.db"` fallback and the CLI doesn't, `prisma migrate deploy` aborts ("datasource.url property is required") while the app silently connects to an empty, table-less DB, so every query 500s ("no such table", surfaced to the UI as "Erro inesperado"). Keep both fallbacks aligned, expose a `db:setup` (`prisma migrate deploy`) npm script, and run `npm run db:setup` in EVERY fresh worktree before hitting the API — the SQLite file is gitignored and not shared across worktrees, and node_modules parent-walk-up doesn't cover the DB file (added 2026-07-23)
- [browser-preview] Any state read in the SAME `javascript_tool` call as the thing that changes it reports the PRE-change value — React commits renders asynchronously (a just-opened modal reads `open:false`) and CSS holds `visibility` for the full `--duration-fast` (a just-revealed tooltip reads `hidden`). ALWAYS re-read in a SEPARATE call before concluding the code is broken; both traps cost a wrong diagnosis here. Combined with the missed-click gotcha (a ref click can land on nothing), confirm via a fresh read plus `read_network_requests`, never the click tool's own success message (added 2026-07-23, merged 2026-07-25)
- [architecture] Adding a new Prisma relation FK defaults to `ON DELETE RESTRICT` (Prisma's implicit default) — this can silently break an EXISTING sibling delete endpoint that doesn't handle the resulting `P2003` error code. Confirmed in practice: adding `Recurrence.owner → Person` made `DELETE /api/people` (untouched, already-shipped code) throw an uncaught `PrismaClientKnownRequestError` → HTTP 500 with no JSON body, breaking the `{error:{message,code}}` envelope contract, whenever the person still has a recurrence. When adding a new relation FROM entity A TO entity B, audit every existing delete handler on B for `P2003` handling — don't assume only the new entity's own routes need error-code coverage. Corollary (added 2026-07-24, `Movement.owner → Person`): once a SECOND entity references the same parent, also generalize the handler's already-correct P2003 *message* — `DELETE /api/people` mapped P2003 → 409 "Pessoa possui recorrências vinculadas", which became a lie for a person blocked only by a movement; widen it to a neutral "Pessoa possui registros vinculados" (added 2026-07-23)
- [architecture] A domain entity field typed as a literal union (e.g. `type: "income" | "expense"`) has no Prisma enum behind it in this codebase (project convention: no Prisma enums — `type String` + `z.enum` at the route boundary) — so the generated Prisma client types it as plain `string`, and a repository method returning the raw Prisma row fails `tsc` against the narrower domain type. Person/Goal never hit this since neither has a literal-union field. Fix is an explicit `as Promise<Entity>` cast on the repository method (with a `ponytail:` comment noting Zod already guards the value at the write boundary) — expect this on every future entity with a literal-union field, not just this one (added 2026-07-23)
- [architecture] Persisted client state (`localStorage`) that stores a REFERENCE to another mutable entity's id — not a fixed enum like `ThemeToggle`'s `"light"|"dark"` — goes stale forever if the referenced entity is later deleted, unless something reconciles it once that entity's list loads. Confirmed in `ProfileProvider`: deleting the person behind the active `profile` left the derived `label` correctly falling back to "Família" (so the UI looked fine), but the raw `profile` id and `localStorage["profile"]` kept the dangling id indefinitely — invisible today, but any future consumer that filters by comparing the raw id (not the label) would silently render empty instead of falling back to "show all". Fix: once the referenced list has actually finished loading (guard on a loaded flag, not just a non-empty check, or a fresh unmatched pick gets wrongly reset), add an effect that resets to the safe default when the stored id no longer matches anything (added 2026-07-23)
- [prisma/migrate] For a Prisma+SQLite schema change that must PRESERVE existing data (e.g. splitting `rangeStart`/`rangeEnd` into a `RecurrenceMonth` child table), generate with `npx prisma migrate dev --name X --create-only` then hand-edit the SQL: a column drop is a table REBUILD (CREATE new_ / INSERT…SELECT / DROP / RENAME), so put the data-backfill INSERT AFTER the new child table's `CREATE TABLE` but BEFORE that rebuild block — it must read the old columns while they still exist. YYYYMM is monotonic as an int, so a recursive CTE expands a range month-by-month (`CASE WHEN m%100=12 THEN (m/100+1)*100+1 ELSE m+1 END`, `WHERE m<endM`); use `lower(hex(randomblob(16)))` for raw-insert ids since `@default(cuid())` only fires for Prisma-issued writes. Neither `migrate dev --create-only` nor `migrate deploy` regenerates the client — run `npx prisma generate` after any schema edit or the build/types stay stale. Verify by seeding old-schema rows in a throwaway db and applying the migration (added 2026-07-24)
- [biome/react] Biome's react-recommended `noArrayIndexKey` fails lint on `key={index}` in a `.map`. For a dynamic list of rows without natural ids (user adds/removes intervals), give each row a stable key from a monotonic `useRef` counter in the state hook (`{...it, key: nextKey.current++}`), never the index — index keys also mis-associate controlled rows across a middle removal. Extracting that keyed-row state into its own `*.hook.ts` sibling doubles as the fix when a form `hook.ts` outgrows the 100-line cap (added 2026-07-24)
- [react/browser-preview] A controlled input that reformats its value on EVERY keystroke (e.g. `MoneyInput`, integer-cents re-derived via `formatCents`/`digitsToCents`) needs THREE caret handlers to stop a mid-field / left-of-comma insert from shifting the value by a decimal place (R$ 6,00 → R$ 600,00): `onFocus` → caret-to-end; a post-reformat `useLayoutEffect` keyed on the formatted string (reference the string itself, e.g. `display.length`, inside the effect body — reading the equivalent off the ref instead makes Biome's `useExhaustiveDependencies` flag the dep as unnecessary); AND `onSelect` that snaps a *collapsed* caret to the end but leaves a range selection (`selectionStart !== selectionEnd`) intact, so select-all-to-replace still works and there's no re-fire loop. The effect alone fires one keystroke too late — the `onSelect` closes that gap. When e2e-driving such a field, send ONE key per `computer.type` call and read the result in a SEPARATE call: a multi-char string ("600") races the controlled re-render and compounds intermediate digits ("6000,00"), a machine-speed artifact real human cadence never hits (added 2026-07-24)
- [typescript/react] `Partial<P>` — and `Partial<X & P>`, and the distributed `Partial<X> & Partial<P>` — is opaque while `P` is an unresolved type parameter: NOTHING is assignable to it, so a component generic over its own payload cannot accept a seed from its caller without an unverifiable cast. Practical rule when unifying two near-identical components: if the divergence is a single RENDERING seam, keep the component non-generic and pass that seam as a `ReactNode` prop (worked twice — `EntryRow`'s period cell, `EntryForm`'s period control); if the divergence spans value + control + validity + payload at once, don't genericize at all — share the concrete half (fields whose types are identical across entities) as a plain component + hook, and let each feature compose its own concretely-typed payload. The payload must never flow through the shared code; that is exactly what removes the need for both the generic and the cast. Corollary on file layout: a folder's `hook.ts` is called by its OWN `index.tsx` — a hook meant for other components to call takes a role-suffixed name (`entry-form.hook.ts`) so readers don't look in the wrong file, and its pure parts move to a tested `*.helper.ts`; a new shared component still gets the full index/hook/style split even when the hook only wraps a one-line change adapter (owner's call, `SelectField` mirroring `TextField`) (added 2026-07-24)
- [review] Before asserting — in a code comment OR a PR body — that a type-level constraint is load-bearing, DELETE it and run `npx tsc --noEmit`: a claimed rationale for `T extends Entry & Partial<V>` ("this is what makes `initial={modal.entry}` typecheck") was simply false, the constraint was inert, and a separate union was doing the work. A reviewer caught it by testing rather than reading. Same discipline for green-check claims: disclose remaining pre-existing failures UNIFORMLY across lint/tsc/test — a body that discloses them for lint but says only "zero new errors" for tsc reads as selective. (added 2026-07-24)
- [tooling] `npm run test` run from the MAIN checkout globs the nested `.claude/worktrees/*` checkouts too, reporting 51 files / 314 tests where the repo itself has 16 / 95 — vitest's default include has no worktree exclusion. Any baseline or "tests still green" claim must be measured from INSIDE a worktree (or with an explicit path filter), or it silently counts other branches' tests as your own (added 2026-07-25)
- [tooling] `npm run lint:fix` is `biome check --write .` — it rewrites the WHOLE repo, including the pre-existing baseline errors in unrelated files (`.design-sync/gen-cards.mjs`), quietly pulling them into your PR; `npm install` likewise rewrites a `hasInstallScript` line in `package-lock.json` even when the task adds no dependency. After either command, `git status` and `git checkout --` anything outside the task's scope BEFORE committing — a reviewer reads unrelated churn as scope creep, and reverting the lint fix also preserves the baseline the DoD is measured against (added 2026-07-25)
- [design-system] `src/styles/README.md` rule 7 (hit targets >= 44px) binds every NEW interactive element, not just the ones reusing `IconButton` — a task file saying "don't reuse IconButton" waives the component, never the rule, and a 14px lucide icon in a bare `<button>` is half the minimum. There is no hit-target token; hardcode `44px` as `IconButton`/`ColorPicker` do. When padding would shift the surrounding layout, use an overlaid centered `::after` (44x44, `translate(-50%,-50%)`) — the element stays its visual size, the focus ring stays tight, and for a tooltip the overlay doubles as the bridge across the gap to its bubble, without which the bubble is unreachable by pointer under `prefers-reduced-motion` (WCAG 1.4.13 Hoverable, since the duration tokens collapse to 0ms). Dismissal for the same criterion must NOT move focus — `blur()` is the thing it forbids; use a state flag re-armed on blur/pointer-enter, plus `stopPropagation()` so the keypress does not also close a surrounding native `<dialog>` (added 2026-07-25)
- [design-system] The LIGHT theme's semantic accents fail `src/styles/README.md` rule 7's contrast floor and this is PRE-EXISTING, not something a new screen introduces: `--color-positive` (`--green-500` #1fb86a) is 2.59:1 on `--color-surface` and 2.33:1 on `--color-bg` — under even the 3:1 large-text floor — and `--color-negative` (`--red-500` #f0453d) is 3.73:1, which clears large text but not the 4.5:1 body floor where `EntryRow` already uses it at `--text-base`. Dark passes comfortably (10.37:1 / 5.65:1), so this is light-only. The owner chose (2026-07-25) to keep the vivid palette and defer the fix, so do NOT special-case a component's colour to dodge it and do NOT write "legible in both themes" into a DoD — measure, or omit the claim. Remediation when it is taken up: #0a7d43 (5.21:1) and #d32118 (5.25:1) clear the body floor on both light surfaces. Two more measured on PR #48, same standing decision applies: `--white` on `--color-brand` is **3.72:1 in DARK** — that is `NavItem`'s `[aria-current="page"]` label at `--text-base`, pre-existing and shipped today; and a design source's own colour picks are not pre-cleared — the Monevo rail specified `--ink-500` on `--ink-900` (3.92:1, fails), corrected to `--ink-400` (7.30:1) before porting. Measure every pair you port from a design file, and never write "legible in both themes" into a PR body without the numbers beside it (added 2026-07-25, extended 2026-07-27)
- [testing] "This can't be tested" is a claim to VERIFY, never to assert — write the throwaway test, run it, delete it, and only then write the waiver. The no-jsdom/no-@testing-library limit blocks RENDERING; it does NOT block a `hook.ts` that happens to call no React hook, and ARCHITECTURE names `hook.ts` itself as a test target. This has now been waived falsely THREE times (`useStatCard`, then five list-card hooks) and a reviewer wrote passing cases each time under the existing config with no new dependency. The second lapse shipped a real bug: an untested `empty` guard let a monthly ceiling of 0 render twelve green "0% used" rows (added 2026-07-25)
- [design-system] A bar/meter is a length AND a colour, and both encode something — they must encode the SAME quantity, and that quantity must appear in text at least once. Shipped backwards here: the coverage meter's length measured `recorded` while its red tone, its worst-first sort and its "faltam R$ X" label all measured the shortfall, so the months with nothing recorded drew EMPTY red bars and the best month drew a nearly full one. Before shipping a meter, state in one sentence what a fuller bar means and check the tone, the sort order and the row's own text all agree with it (added 2026-07-25)
- [architecture] For a nullable money setting, `0` is a REACHABLE saved value, not a synonym for unset: `MoneyInput` seeds its field to 0, Save gates only on `loaded`, and `settings/route.ts` accepts `.min(0)`. The codebase already treats 0 as unset in two places — `limit.helper.ts` via `goalCents ? … : null` and `MonthlyGoalSection` via `savedGoalCents > 0 ? … : "—"` — so a new consumer checking `=== null` silently disagrees with both. Use falsiness (`!goalCents`) and grep the existing render sites for the convention before picking a comparison (added 2026-07-25)
- [review] After fixing a review finding, test the invariant the FIX could break, not just the property it fixed — and mutate the fix to prove the new test bites. Cost two rounds on one PR: deriving a per-chart axis margin fixed a clipped label and silently misaligned the two charts by up to 11px, and the replacement test (`expect(barFrame().left).toBe(lineFrame().left)`) was tautological because `left` no longer depended on the argument being varied. A fix that ships with a green suite it cannot fail is not verified (added 2026-07-25)
