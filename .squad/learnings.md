# Learnings — Pocket Squad

Durable, one-line rules. Appended by /ps:publish after each merge; read by
/ps:story during refinement. A rule must change future behavior — otherwise
delete it. Cap: 30 rules; when adding past the cap, delete the weakest one.

Format: `- [scope] imperative rule (added YYYY-MM-DD)`

---

- [worktree] After EnterWorktree, immediately rename the branch to ps/<story-slug>/<task-slug> — it auto-generates worktree-ps+<slug>+<task> (/ → +), breaking the ps/<slug>/* convention /ps:load's PR cross-check relies on (added 2026-07-21)
- [worktree] A tool that derives a name from cwd (create-next-app ., npm init, etc.) can fail inside an EnterWorktree directory since its +-joined basename isn't a valid npm package name — scaffold into a throwaway subdir first, then move the generated files up (added 2026-07-21)
- [biome] Run `npx biome explain <rule>` before trusting any rule snippet — create-next-app's pinned Biome version can predate a rule entirely (noExcessiveLinesPerFile needs >=2.3.12), and a rule's group (style/complexity/nursery) shifts across releases (added 2026-07-21)
- [publish] `gh pr merge --delete-branch` routinely fails to delete the branch (local and/or remote) whenever it's checked out in any worktree — expected here, since this workflow leaves each task's worktree in place until an explicit cleanup step. Treat the failure as normal: confirm the merge itself succeeded via `gh pr view --json state,mergedAt`, then `git worktree remove` the task's worktree, `git branch -D` the local branch, and `git push origin --delete` the remote one — verify the remote is actually gone with `git ls-remote --heads`, since a failed local deletion seems to abort before remote deletion runs (added 2026-07-21)
- [publish] After ExitWorktree removes a worktree whose branch was renamed post-creation, check `git branch --list "ps/*"` for a survivor — it only deletes the name it originally auto-generated, leaving a rename behind for a manual `git branch -D` (added 2026-07-21)
- [worktree] /ps:story's story/task `.md` files sit uncommitted on the main checkout; `git worktree`/EnterWorktree branches from committed history, so /ps:run must copy them into the task's worktree, commit them there, AND delete the main checkout's now-stale untracked copy — otherwise the task's "check the box" step has nothing to edit, and the leftover copy trips /ps:publish's dirty-checkout preflight later (added 2026-07-21)
- [publish] `gh pr merge` itself (not just its `--delete-branch` flag) can fail with `fatal: 'main' is already used by worktree` when run while cwd is inside another worktree of the same repo — ExitWorktree back to the main checkout before calling `gh pr merge`, not only before the later branch-cleanup step (added 2026-07-21)
- [browser-preview] `preview_start`'s `{name}` launcher always runs from the main checkout's directory, never from a task's EnterWorktree cwd — to visually verify a worktree-isolated change, start the dev server manually from inside the worktree on a spare port, then `preview_start` with `{url: "http://localhost:<port>"}` (added 2026-07-21)
- [worktree] `git worktree remove` can refuse with "cannot remove a locked working tree" when an EnterWorktree lock from an earlier command-turn is still registered but ExitWorktree now no-ops ("no active EnterWorktree session") for that path — confirm `git status` is clean first, then `git worktree unlock <path>` and retry the normal (non-forced) `git worktree remove`, rather than reaching for `-f -f` (added 2026-07-21)
- [storybook] A Foundations-only Storybook (MDX `<Meta>` docs, no CSF stories) breaks `@storybook/addon-themes`'s theme decorators — they only run inside a story's render (a `useEffect` in the returned decorator function), so the toolbar updates Storybook's internal globals/URL but never writes `data-theme` to the DOM for a docs-only page. Fix: wire the toggle directly via `globalTypes`/`initialGlobals` + `addons.getChannel().on("updateGlobals", ...)` in `preview.ts` instead (drop the addon) — works for both docs-only pages and future CSF stories alike. Revisit once real component stories land (added 2026-07-21)
- [storybook] `@storybook/addon-docs`'s typography reset overrides `font-family` (and likely `color`) directly on `div`/`p`/`span`/`code` inside MDX docs pages — inheriting a token from a wrapping element is not enough, it must be set as an inline style on the exact leaf element rendering the text, or it silently falls back to Storybook's own UI font (added 2026-07-21)
- [storybook] MDX auto-wraps any bare literal text that's the child of a hand-authored JSX block element (div, p, ...) in an implicit `<p>` — even inside an already-authored `<p>`, producing invalid nested `<p><p>...</p></p>` and a React hydration-mismatch console error. Only a JS expression child (`{"text"}`, `{name}`, or a real JSX element) is exempt. Also: Storybook's docs canvas background never follows `[data-theme]` (it's always white), so any specimen relying on inherited `--color-text` washes out in dark mode — give every text specimen its own explicit `background` + `color`, not just `font-family` (added 2026-07-21)
- [css] Never mix a `:hover` (or other pseudo-class) CSS rule with an inline `style={{...}}` on the same property on the same element — the inline style always wins regardless of the pseudo-class matching, so the hover state silently never applies. The property that needs to change on `:hover` (or focus/active) must live in an actual stylesheet/class rule, not inline; this bit a "hover to preview" demo where the box never visibly changed color despite `:hover` correctly matching and the transition firing (added 2026-07-21)
- [design-system] A blur-shadow token calibrated against the app's own `--color-bg` (e.g. `--elevation-overlay`) reads as almost invisible when demoed directly on a plain white/neutral canvas (Storybook's docs page, a blank page, an isolated snippet) — always demo it on a `--color-bg`-painted backdrop, matching the real contrast it'll have in the actual app, or it looks broken even though the token value is correct (added 2026-07-21)
- [design-system] A semantic token meant to contrast with a sibling (e.g. `--color-surface-raised` vs `--color-surface`, for `:hover`/elevation) can be declared identically in one theme and still pass `tokens.test.ts` — that test only checks a token is declared in both themes, not that it differs from what it's meant to contrast with. First real `:hover`/raised-surface consumer silently breaks until someone checks. Verify by reading `getComputedStyle` under a real `:hover` match in every theme, not by eyeballing hex codes (added 2026-07-21)
- [worktree] The auto-mode classifier blocks `rm -rf` on the main checkout even for a stale untracked copy that's safe to discard (e.g. the leftover from the /ps:story-files-copy step above) — use `mv` to relocate it (scratchpad, or anywhere outside the repo) instead of deleting; that's reversible and isn't blocked (added 2026-07-21)
- [run] Before warning the owner that a task's dependency isn't checked in `story.md`, `git pull` and re-check the dependency PR's state first — it can merge out-of-band between conversation turns (owner, another session) without the local checkout or loaded context knowing, silently resolving what looked like a blocker (added 2026-07-21)
- [worktree] `node_modules` is never shared across git worktrees — a dependency installed in one task's worktree (e.g. `npm install lucide-react`) only lands in that worktree's `package.json`/lockfile once its PR merges, but the *next* task's worktree branches from that updated main with the manifest correct and `node_modules` still empty of it. `npm run lint`/`test` can still pass by resolving pre-existing packages from the main checkout's `node_modules` (Node's parent-directory walk-up, since worktrees live nested under `.claude/worktrees/`), masking the gap until `next build` actually tries to bundle the new import. Run `npm install` at the start of any task whose "Depends on" installed a package (added 2026-07-22)
- [review] Before a PR body claims a specific artifact was added exactly as the task file prescribed (a `ponytail:` comment, a particular pattern), grep the actual diff to confirm — a prior task dropped a prescribed comment during implementation but the PR description still claimed it was there, caught only by a fresh-eyes reviewer diffing the claim against the code (added 2026-07-22)
- [browser-preview] `read_page` called immediately after `navigate` can return `(empty page)` / `Viewport: 0x0` even though the page loaded correctly (confirmed via `computer{screenshot}` showing real content) — this is a stale-cache artifact of the tool, not a real load failure. Just retry `read_page` once rather than investigating further (added 2026-07-22)
- [worktree] `EnterWorktree` refuses to run from inside an `Agent`-tool-spawned subagent (cwd-override restriction) — when dispatching parallel `/ps:run` tasks via `Agent`, have each subagent go straight to `git worktree add -b ps/<slug>/<task> <path>` instead of attempting `EnterWorktree` first; the tool only works from the top-level session, not a spawned subagent (added 2026-07-22)
- [publish] After a task's PR merges, `git checkout <base>` + `git pull --rebase` in the main checkout can abort with `error: The following untracked working tree files would be overwritten by merge` if the checkout still holds the pre-merge untracked story/task `.md` copy (see the `/ps:story`-files rule above) — the incoming commit now tracks those exact paths. `mv` the untracked copy to scratchpad (never `rm`, per the rule above) and retry; safe since the merged commit already carries the authoritative content (added 2026-07-22)
- [worktree] Running 2+ `/ps:run` tasks in parallel off the same pre-merge `main` means each independently commits an identical copy of the story/task `.md` docs — confirmed in practice: once the first PR merges, every other still-open PR's `gh pr view --json mergeable` flips to `CONFLICTING` (add/add on `story.md` only; the 5 task files auto-merge cleanly since content-identical). Resolve in the task's worktree: `git fetch origin && git merge origin/main`, keep every checkbox from both sides checked in `story.md`, `git add` + `git commit --no-edit`, `npm install` (the incoming merge may have added dependencies), rerun the full verification suite, then push — `mergeable` settles to `MERGEABLE` a few seconds later (added 2026-07-22)
