# Adicionar o workflow de CI que reprova o PR

## Context desta tarefa

Depende de **260812-1106** e **260812-1107**, ambas mergeadas quando esta roda. Pode
assumir que existem e saem 0 localmente: `npm run lint` (Biome com
`linter.rules.preset: "all"` + `scripts/check-line-cap.sh`), `npm run typecheck`,
`npm run test:coverage` com `coverageThreshold.global` em 90, e `npm run build`. Pode
assumir que `e2e/` e o Playwright não existem mais.

## Outcome
R1. `.github/workflows/ci.yml` existe, dispara em todo `pull_request` e em `push` para
    `main` e `develop`, e cancela a rodada anterior quando o PR recebe push novo.
R2. O job reprova de verdade: nenhum passo tem `continue-on-error`, `|| true`, `if:
    always()` mascarando falha, ou qualquer forma de engolir exit code.
R3. Numa checagem em CI limpo, os cinco gates rodam e passam: lint (Biome + cap de
    linhas), tipos, testes com cobertura ≥ 90%, build.
R4. O cap de 100 linhas realmente executa no CI — não passa vazio por falta do ref
    `main` no checkout.

## Context

- **Não existe `.github/` neste repo.** Nenhum CI hoje; tudo é local e manual. Este é o
  primeiro workflow.

- **O shape pedido pelo dono**, a ser seguido, com uma remoção e duas adições
  justificadas em `## Design`:
  ```yaml
  name: CI
  on:
    pull_request:
    push:
      branches: [main, develop]
  concurrency:
    group: ci-${{ github.ref }}
    cancel-in-progress: true
  jobs:
    verificar:
      name: Verificar
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - uses: actions/setup-node@v4
          with:
            node-version: 22
            cache: npm
        - run: npm ci
        - name: Lint e formatacao (Biome)
          run: npm run lint
        - name: Tipos
          run: npx tsc --noEmit
        - name: Testes e cobertura
          run: npm run test:coverage
        - name: Build
          run: npm run build
  ```

- **Cuidado — `npm ci` não gera o client do Prisma.** O script chama-se
  `db:postinstall`, que **não** é o lifecycle `postinstall` do npm, então nada roda
  sozinho. E `.gitignore` tem `/src/generated/prisma`, ou seja, o client não está no
  repo. Sem `npx prisma generate` antes, `typecheck`, `test:coverage` e `build` quebram
  todos em `Cannot find module '@/generated/prisma/client'`.

- **Cuidado — o cap de linhas passa vazio num checkout raso.**
  `scripts/check-line-cap.sh` monta a lista de arquivos com
  `git diff --name-only --diff-filter=d "$BASE"...HEAD` (`BASE=${BASE:-main}`) e engole
  o erro com `2>/dev/null`. `actions/checkout@v4` usa `fetch-depth: 1` por padrão, o ref
  `main` não existe no clone, o `git diff` falha, a lista sai vazia e o script imprime
  `line cap: ok` sem ter checado nada — um gate que não reprova.

- **Cuidado — `DATABASE_URL` não existe no CI.** `.env*` é gitignored (só
  `.env.example` entra). `src/infra/db/client.ts` cai no default
  `process.env.DATABASE_URL ?? "file:./dev.db"`, o que basta para gerar o client e
  buildar. Se algum passo pedir a variável, defina-a no `env:` do job como
  `file:./ci.db` — nunca aponte para `dev.db` de verdade.

- **`package-lock.json` está versionado** (é o que faz `cache: npm` funcionar) e é o
  único lockfile. Node local é v25, e nada no repo fixa versão — o `node-version: 22`
  do workflow passa a ser o pin de fato, como o comentário do dono já dizia.

## Design

- **Contract — o passo `Contrato dos JSONs` sai.** `npm run validate:json`,
  `usuarios/`, `fichas/` e `fichas.ts` não existem neste repo e nunca existiram no
  histórico; são de outro projeto. Decisão do dono: remover o passo. Nada o substitui —
  `biome check .`, que já roda no passo de lint, valida sintaxe de JSON.

- **Contract — dois passos entram, nesta ordem, entre `npm ci` e o lint:**
  ```yaml
  - name: Client do Prisma
    run: npx prisma generate
  ```
  e o checkout ganha:
  ```yaml
  - uses: actions/checkout@v4
    with:
      fetch-depth: 0
  ```
- **Chose `fetch-depth: 0` em vez de `git fetch origin main` num passo extra** — um
  campo em vez de um passo, e o `check-line-cap.sh` continua intocado. O custo é o
  clone completo de um repo pequeno.

- **Contract — permissões mínimas** no topo do arquivo, já que nenhum passo escreve
  nada:
  ```yaml
  permissions:
    contents: read
  ```

- **Chose manter `npx tsc --noEmit` literal** no passo `Tipos`, como o dono escreveu,
  em vez de trocar por `npm run typecheck` — é o mesmo comando, e o shape pedido é o
  contrato desta tarefa.

- **Chose um job único e sequencial** (`verificar`) em vez de jobs paralelos por gate —
  paralelizar exigiria `npm ci` e `prisma generate` repetidos em cada job, o que num
  repo deste tamanho custa mais do que economiza, e o dono especificou um job.

## Steps
1. Criar `.github/workflows/ci.yml` com o shape do dono, sem o passo de
   `validate:json`, com `permissions: contents: read`, `fetch-depth: 0` no checkout e o
   passo `npx prisma generate` depois do `npm ci`. → R1 R2 R3
2. Provar localmente que o cap de linhas de fato roda no cenário do CI, e não vazio.
   → R4

## Verify
- R1: `cat .github/workflows/ci.yml` — contém `on.pull_request`,
  `on.push.branches: [main, develop]`, `concurrency.group: ci-${{ github.ref }}` e
  `cancel-in-progress: true`.
- R2: `grep -nE "continue-on-error|\|\| true|if: *always" .github/workflows/ci.yml` —
  retorna vazio.
- R3: a sequência do job, rodada na mão a partir de um clone limpo em `/tmp`, sai 0 em
  cada linha:
  ```
  npm ci && npx prisma generate && npm run lint && npx tsc --noEmit && npm run test:coverage && npm run build
  ```
- R4: no mesmo clone limpo, `BASE=main sh scripts/check-line-cap.sh` com o ref `main`
  presente lista arquivos e sai 0; com `BASE=inexistente` ele imprime `line cap: ok`
  sem checar nada — é esse segundo comportamento que o `fetch-depth: 0` evita.
- Depois de abrir o PR: `gh pr checks <n>` — o check `Verificar` aparece e passa.

## Scope
- In: `.github/workflows/ci.yml`, arquivo novo.
- Out: `package.json` e qualquer script — os comandos já existem e não mudam ·
  `biome.json` · `scripts/check-line-cap.sh` · qualquer arquivo sob `src/` ·
  branch protection e settings do GitHub, que são configuração de repositório e não de
  código.

## Forbidden
- `continue-on-error`, `|| true`, `set +e`, `--passWithNoTests`, `--max-diagnostics` ou
  qualquer flag que faça um gate reprovado virar verde.
- Baixar `coverageThreshold`, desligar regra do Biome ou pular passo para o CI ficar
  verde. Se um gate reprovar, o defeito é do código.
- Adicionar cache de `.next`, de `node_modules` ou de resultado de teste — nada além do
  `cache: npm` do `setup-node`.
- Segredos, tokens, `permissions: write-all`, deploy, publicação de artefato ou
  qualquer passo que fale com serviço externo.
- Reintroduzir o passo `validate:json` ou criar um script `validate:json` para
  justificá-lo.
