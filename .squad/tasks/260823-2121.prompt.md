# Distinguir tipos de cifra e honrar a meta no cap

## Outcome

R1. Cada cifra visível no dashboard `ok` declara o tipo de fato: teto (gasto possível agora), projetado (saldo no fim do período), meta (teto limitado pela meta mensal salva) e simulação (cenário). Teto e projetado não compartilham o mesmo peso tipográfico nem o mesmo rótulo.
R2. Com meta mensal salva (`data.meta !== null`) e sem cap persistido, o cap inicial é `"meta"`, não `"50"`. Sem meta, o inicial continua `"50"`.
R3. A escolha de cap sobrevive a reload da página (mesmo padrão de persistência da simulação). Sem storage, vale R2.
R4. `SimulationSelect` tem rótulo visível. Com valor `"all"`, a faixa herói marca que as cifras incluem simulações.

## Design

- **Contract** — persistência do cap, espelhando a simulação:

```
KEY = "ceiling-cap"
isCap(value): value is CeilingCap  // membro de CEILING_CAPS
```

Seed após hydrate: storage válido → esse cap; senão `data.meta !== null` → `"meta"`; senão `DEFAULT_CEILING_CAP`. Troca no `CapSelector` grava o KEY.

Rótulos (pt-BR, visíveis): teto = gasto possível agora / extra este mês; projetado = saldo projetado em {mês}; quando cap é `"meta"`, a faixa ou o card nomeia “limitado pela meta”; simulação = o select com `<label>` visível + marca na faixa se `"all"`.

- **Flow** — meta apagada em Configurações enquanto o storage diz `"meta"`: o fetch seguinte trata como hoje (`meta` → 50 no servidor) e a UI não deixa `"meta"` selecionado sem `hasMeta`.
- **Chose** persistir cap como a simulação **over** deixar cap volátil — a auditoria: o cap é a mesada; a simulação é o what-if, e hoje está invertido.
- **Chose** default `"meta"` quando existe meta salva **over** default `"50"` — a Meta de Configurações é a regra que o dono já escreveu.
- **Chose** rótulo + peso **over** um quarto matiz de marca — cobalto continua só sinal; tipo de fato não vira cor decorativa.
