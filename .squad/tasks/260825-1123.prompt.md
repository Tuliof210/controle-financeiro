# Persistir teto, objetivos e simulação nas configurações

## Outcome
R1. `GET /api/settings` responde `{ data: null }` quando nunca houve linha salva e, quando
    houve, um objeto com os sete campos `ceilingMode`, `ceilingPercent`, `ceilingCents`,
    `goalsMode`, `goalsPercent`, `goalsCents`, `showSimulated`.
R2. `PUT /api/settings` aceita esse objeto inteiro e persiste; responde 422 `validation`
    quando `*Mode` não é `"percent"`/`"fixed"`, quando `*Percent` sai de 0..100 ou quando
    `*Cents` sai de 0..`MAX_CENTS`.
R3. O valor em centavos já salvo no `dev.db` do dono continua legível depois de
    `npm run db:setup` — a coluna é renomeada, nunca recriada.
R4. `GET /api/dashboard?owner=…&cap=…&simulation=…` responde exatamente como hoje (mesmos
    números, mesmos alvos `25/50/75/meta`, mesma regra de simulação), e `ceiling` passa a
    trazer `headroomCents`.
R5. A tela `/configuracoes` continua carregando e salvando a meta mensal sem regressão.

## Context
Este é o primeiro de três prompts. Ele só prepara o modelo: **nenhum comportamento visível
muda**. `260825-1124` constrói a tela de Perfil sobre estes campos; `260825-1125` faz o
dashboard obedecê-los e remove os controles de lá.

- **Imitate** — a fatia vertical de `Settings` já existe inteira e é o molde. Para
  acrescentar um campo persistido são quatro arquivos, nunca um endpoint novo:
  `prisma/schema.prisma` → `src/core/entities/settings.entity.ts` → o `shape` de
  `src/infra/repositories/settings.prisma.repository.ts` → o `saveSchema` de
  `src/app/api/settings/route.ts`. O `PUT` recebe o objeto todo e
  `saveSettings(parsed.data)` repassa sem tocar.

- **Reuse** `src/infra/repositories/settings.prisma.repository.ts`, verbatim — o upsert do
  singleton já está pronto e só o `shape` cresce:
  ```ts
  const SETTINGS_ID = 1;
  const shape = { monthlyGoalCents: true } as const;

  export const settingsRepository: SettingsRepository = {
    get() {
      return prisma.settings.findUnique({ where: { id: SETTINGS_ID }, select: shape });
    },
    save({ monthlyGoalCents }) {
      return prisma.settings.upsert({
        where: { id: SETTINGS_ID },
        create: { id: SETTINGS_ID, monthlyGoalCents },
        update: { monthlyGoalCents },
        select: shape,
      });
    },
  };
  ```

- **Imitate** `src/lib/simulation.ts` inteiro — é a convenção da casa para um vocabulário
  que as duas pontas do fio leem, e é exatamente a forma que `DEFAULT_SETTINGS` deve ter:
  ```ts
  export const SIMULATION_VIEWS = ["real", "all"] as const;
  export type SimulationView = (typeof SIMULATION_VIEWS)[number];
  export const DEFAULT_SIMULATION_VIEW: SimulationView = "real";
  ```

- **Reuse** o `saveSchema` de `src/app/api/settings/route.ts`, que já carrega as duas
  decisões que valem para os novos campos — `min(0)` porque zero é como se desliga um
  ajuste (não existe DELETE), e `max(MAX_CENTS)` porque é o teto do `Field money`:
  ```ts
  const saveSchema = z.object({
    monthlyGoalCents: z.number().int().min(0).max(MAX_CENTS),
  });
  ```

- **Reuse** `buildCeiling` em `src/app/api/dashboard/ceiling.helper.ts` — assinatura atual,
  que este prompt **não** altera (é o `260825-1125` que a troca):
  ```ts
  export function buildCeiling(
    points: MonthPoint[],
    currentMonth: number,
    cap: number,          // percentagem: 25 | 50 | 75 | 100-para-meta
    limit: number | null, // centavos, teto duro do mês; null nos alvos percentuais
  ): Ceiling
  ```
  Dentro dele, `const worst = suffixMinimum(ahead)` e
  `const red = ahead.find((point) => point.cumulative < 0)` já são exatamente os dois
  ingredientes de `headroomCents` — nada de aritmética nova.

- **Reuse** `src/app/api/dashboard/dashboard-inputs.helper.ts` — é o único lugar que lê a
  coluna hoje, e o único que precisa acompanhar o rename:
  ```ts
  function metaOf(monthlyGoalCents: number | undefined): number | null {
    if (!monthlyGoalCents) { return null; }   // zero lê como "não configurado"
    return monthlyGoalCents;
  }
  ```
  Chamado em `src/app/api/dashboard/service.ts` como
  `const meta = metaOf(settings?.monthlyGoalCents);`.

- **Watch out for** o `Settings` do Prisma ser um singleton pinado em `id 1`, e o comentário
  do schema (`prisma/schema.prisma:84-93`) registrar por que: `rangeStart`/`rangeEnd` foram
  removidos de propósito porque o período é derivado das entradas, e a linha não tem
  `ownerId` porque o ajuste é da família toda. Os campos novos herdam as duas regras.

- **Watch out for** `get()` devolver `Settings | null`, e `null` significar "nunca foi
  salvo". Isso **não** muda: quem lê é que aplica `DEFAULT_SETTINGS`. Trocar o `null` por um
  objeto default no repositório apagaria a distinção que a tela de Perfil vai precisar.

- **Watch out for** `src/app/configuracoes/.../SpendingGoalSection/hook.ts` fazer
  `apiPut("/api/settings", { monthlyGoalCents: cents })`. Como o `PUT` recebe o objeto
  inteiro, renomear a coluna sem mexer nesse hook quebra a tela em runtime sem quebrar o
  typecheck se o tipo for frouxo — o hook tem que passar a enviar os sete campos.

- **Watch out for** `npm run db:clean` listar as tabelas por nome
  (`DELETE FROM Settings; …`). O nome da tabela não muda, então o script continua válido —
  confirme antes de editá-lo.

- **Watch out for** o cap de 100 linhas contar linhas simples (comentários e brancos
  incluídos) em todo arquivo `.ts`/`.tsx`/`.scss` sob `src` que o branch tocar,
  `src/generated/` fora. `route.ts` de settings está em 36 linhas e cresce com o schema.

## Design
- **Contract — `prisma/schema.prisma`, model `Settings`.** Sete colunas, a primeira
  renomeada e as seis últimas novas:
  ```prisma
  model Settings {
    id             Int     @id @default(1)
    ceilingCents   Int     @default(0)
    ceilingMode    String  @default("percent")
    ceilingPercent Int     @default(50)
    goalsMode      String  @default("percent")
    goalsPercent   Int     @default(25)
    goalsCents     Int     @default(0)
    showSimulated  Boolean @default(false)
  }
  ```
  `monthlyGoalCents` → `ceilingCents`: o nome antigo passou a colidir de frente com o novo
  ajuste de objetivos (`goalsCents`), e o que a coluna sempre guardou é o teto mensal em
  centavos. Os defaults reproduzem o comportamento de hoje — `50` é o
  `DEFAULT_CEILING_CAP`, `25` é o `PACE_DIVISOR = 4`, `false` é o
  `DEFAULT_SIMULATION_VIEW = "real"`.

- **Contract — a migration.** Um arquivo novo em `prisma/migrations/`, **escrito à mão**,
  com `ALTER TABLE "Settings" RENAME COLUMN` para a primeira e um `ALTER TABLE … ADD COLUMN
  … NOT NULL DEFAULT …` para cada uma das seis. Nada de rebuild de tabela: o SQL que o
  `prisma migrate dev` gera para SQLite recria a tabela e é o caminho que perde a linha do
  dono. Se o `prisma migrate dev` insistir em gerar o rebuild, gere e **substitua o corpo
  do `.sql`** pelos `ALTER TABLE`, mantendo o nome da pasta.

- **Contract — `src/core/entities/settings.entity.ts`.** A entidade espelha as sete
  colunas (sem `id`, que segue detalhe de persistência), e os dois modos ganham o
  vocabulário compartilhado:
  ```ts
  export const SETTING_MODES = ["percent", "fixed"] as const;
  export type SettingMode = (typeof SETTING_MODES)[number];

  export interface Settings {
    ceilingMode: SettingMode;
    ceilingPercent: number; // 0..100
    ceilingCents: number;   // 0..MAX_CENTS
    goalsMode: SettingMode;
    goalsPercent: number;   // 0..100
    goalsCents: number;
    showSimulated: boolean;
  }
  ```
  `SETTING_MODES` mora na entidade e não em `src/lib/`, porque é o domínio do ajuste, não
  um detalhe de transporte — e o `z.enum(SETTING_MODES)` do route lê daqui, do mesmo modo
  que o route do dashboard já lê `z.enum(SIMULATION_VIEWS)`.

- **Contract — `src/lib/settings-defaults.ts`.** Uma constante só, `DEFAULT_SETTINGS:
  Settings`, com os mesmos valores dos `@default` do schema. É o que a tela usa quando
  `GET` devolve `null`, e o que o dashboard usa quando não há linha — as duas pontas leem
  daqui, como `CEILING_CAPS` e `SIMULATION_VIEWS` já fazem, para que "nada salvo" signifique
  a mesma coisa nos dois lados.

- **Contract — `Ceiling` ganha `headroomCents`** em
  `src/app/api/dashboard/ceiling.types.ts`:
  ```ts
  headroomCents: number; // centavos, >= 0
  ```
  Definição: o teto mensal máximo que ainda não deixa nenhum mês futuro no vermelho — o
  `budget` que o primeiro mês receberia com alvo de 100% e sem limite, isto é
  `suffixMinimum(ahead)[0]`, e `0` quando já existe mês no vermelho (`red !== undefined`).
  Não depende do `cap` nem do `limit` recebidos: é o mesmo número em qualquer alvo, porque
  é isso que a tela de Perfil vai usar para travar o input em valor fixo.

- **Flow — o `PUT` continua sendo tudo-ou-nada.** Não há PATCH por campo: `saveSchema`
  exige os sete, e `upsert` grava os sete. Quem edita um card na tela manda os outros seis
  como estão. Consequência que o `260825-1124` herda: cada card precisa do objeto inteiro
  carregado antes de poder salvar.

- **Chose renomear a coluna over manter `monthlyGoalCents`** — manter era um diff bem menor
  (só `ADD COLUMN`), mas deixaria `monthlyGoalCents` e `goalsCents` lado a lado significando
  coisas diferentes, e é o segundo que tem a ver com objetivos.

- **Chose um `headroomCents` no payload over um endpoint novo** tipo
  `GET /api/ceiling-limits` — o número sai de dentro do `buildCeiling` que já roda, e a tela
  de Perfil já vai ter que chamar `/api/dashboard` de alguma forma para saber o máximo.

- **Chose manter `?cap=`/`?simulation=` e o campo `meta` do payload** — trocá-los é o
  `260825-1125`. Aqui eles só passam a ler `ceilingCents` no lugar de `monthlyGoalCents`, e
  R4 é a prova de que nada mais se moveu.

## Steps
1. Renomear a coluna e acrescentar as seis no `schema.prisma`, com a migration à mão
   (`RENAME COLUMN` + `ADD COLUMN … NOT NULL DEFAULT`), e rodar `npm run db:setup`. → R3
2. Estender `settings.entity.ts` com `SETTING_MODES`/`SettingMode` e os sete campos, e o
   `shape`/`create`/`update` de `settings.prisma.repository.ts`. → R1
3. Criar `src/lib/settings-defaults.ts` com `DEFAULT_SETTINGS`. → R1
4. Estender o `saveSchema` de `src/app/api/settings/route.ts` com os sete campos e suas
   faixas. → R2
5. Fazer `dashboard-inputs.helper.ts` e `service.ts` lerem `ceilingCents` no lugar de
   `monthlyGoalCents`, sem mudar o comportamento do alvo Meta. → R4
6. Acrescentar `headroomCents` a `Ceiling` e calculá-lo em `buildCeiling`. → R4
7. Fazer o `onSave` de `SpendingGoalSection/hook.ts` enviar o objeto de sete campos
   (partindo do que o `GET` trouxe, ou de `DEFAULT_SETTINGS` quando veio `null`). → R5
8. Atualizar os testes existentes que fixam a forma antiga e acrescentar os casos novos:
   `src/infra/repositories/tests/settings.prisma.repository.test.ts`,
   `src/app/api/settings/tests/{service,route}.test.ts`,
   `src/app/api/dashboard/tests/{ceiling.helper,service-inputs}.test.ts`,
   `src/app/configuracoes/.../SpendingGoalSection/tests/hook.test.ts`, e um teste novo para
   `settings-defaults.ts`. → R1 R2 R4 R5

## Verify
- R1 R2 R5: `npm run test` — suíte inteira verde (baseline hoje: 311 suítes, 1186 testes).
  Os testes de `route.test.ts` cobrem a faixa de cada campo; os de

## Forbidden
- Não altere a assinatura de `buildCeiling` nem de `savingPace`. `headroomCents` é um campo
  a mais no retorno, não uma entrada a mais.
- Não deixe o `prisma migrate dev` recriar a tabela `Settings`. Nenhuma migration já
  aplicada em `prisma/migrations/` pode ser editada.
- Não faça `settingsRepository.get()` devolver `DEFAULT_SETTINGS` no lugar de `null`.
- Não introduza um `PATCH` nem um endpoint por campo em `/api/settings`.
- Não acrescente `ownerId` ao `Settings`: o ajuste é da família, como a coluna atual.
- Nenhum valor de cor, espaço, raio ou duração hardcoded se algum `.scss` for tocado.
