# Renomear Configurações para Perfil e configurar teto, objetivos e simulação

## Outcome
R1. A rota é `/perfil`, o item do menu diz **Perfil**, e `/configuracoes` não existe mais em
    lugar nenhum do app (nav, `metadata`, `PageHeader`, links de outras telas).
R2. Um card **Teto de Gastos** explica em texto como o teto é calculado e permite escolher
    entre **Porcentagem** e **Valor fixo**. Em porcentagem o input não passa de 100; em
    valor fixo não passa do máximo que não deixa nenhum mês futuro no vermelho, e o card
    diz qual é esse máximo.
R3. Um card **Limite em objetivos** permite de 0 a 100% do teto, em porcentagem ou em valor
    fixo, com os mesmos limites de input do R2.
R4. Um card **Dados simulados** liga e desliga a contagem de previsões simuladas no
    dashboard, e o controle antigo do dashboard continua funcionando enquanto isso.
R5. Um único **Salvar** grava os sete campos de uma vez; ele fica desabilitado enquanto
    nada mudou, e uma linha `role="status"` confirma o salvamento.
R6. Os cards **Pessoas** e **Objetivos** continuam funcionando como hoje, sem regressão.

## Design
- **Contract — a rota e os nomes.** `src/app/configuracoes/` → `src/app/perfil/`. O item do
  `NAV` passa a `{ href: "/perfil", label: "Perfil", icon: "settings" }`, o `metadata.title`
  e o `PageHeader.title` passam a `"Perfil"`, e o `subtitle` passa a descrever a tela toda
  (pessoas, objetivos e os ajustes de exibição). A pasta do componente **continua**
  `_components/SettingsScreen/` e o componente **continua** `SettingsScreen`.

- **Chose manter o nome `SettingsScreen` over renomear para `ProfileScreen`** — já existem
  `ProfileProvider`, `ProfileSelect` e `profile.helper.ts` falando do *perfil ativo* (qual
  pessoa está selecionada no header). Um `ProfileScreen` que não tem nada a ver com isso é o
  tipo de colisão que custa uma leitura errada por mês. "Perfil" é copy de UI e rota
  (pt-BR); o código segue em inglês e a tela segue sendo a de settings.

- **Contract — o estado mora na tela, não nos cards.** `SettingsScreen/preferences.hook.ts`
  é o dono: um `apiGet<Settings | null>("/api/settings")` (caindo em `DEFAULT_SETTINGS`
  quando vem `null`), um `apiGet<DashboardData>` para o headroom, e um único
  `apiPut("/api/settings", settings)` com os sete campos. Devolve:
  ```ts
  interface Preferences {
    settings: Settings;
    maxCents: number | null; // ceiling.headroomCents; null quando status !== "ok"
    dirty: boolean;
    error?: string;
    savedMessage: string;
    onModeChange: (field: "ceilingMode" | "goalsMode", mode: SettingMode) => void;
    onPercentChange: (field: "ceilingPercent" | "goalsPercent", raw: string) => void;
    onCentsChange: (field: "ceilingCents" | "goalsCents", cents: number) => void;
    onSimulatedChange: (value: boolean) => void;
    onSave: () => Promise<void>;
  }
  ```

- **Flow — por que o estado não pode ficar em cada card.** O `PUT` de `/api/settings` é
  tudo-ou-nada: grava os sete campos. Três cards com `apiGet`/`apiPut` próprios (o padrão
  que `PeopleSection`/`GoalsSection` seguem, cada um se buscando) fariam cada salvamento
  sobrescrever os campos dos outros dois com a cópia que aquele card carregou no mount. Por
  isso os três cards novos são apresentacionais e recebem valor + callback; `PeopleSection`
  e `GoalsSection` seguem se buscando, porque falam com outros endpoints.

- **Contract — um form, um Salvar.** Os três cards novos ficam dentro de um
  `<form onSubmit={onSubmitForm(onSave)}>` no `SettingsScreen/index.tsx`, com um `Button
  type="submit"` `disabled={!dirty}` e um `<p role="status">` depois deles. `dirty` é
  comparação com o objeto que o `GET` trouxe.

- **Chose um Salvar para os três cards over um por card** — com o estado compartilhado, três
  botões gravariam exatamente a mesma coisa e três `role="status"` competiriam pelo mesmo
  anúncio. O preço é que marcar "dados simulados" deixou de valer na hora, como valia no
  toggle do dashboard; `disabled={!dirty}` é o que mostra que falta salvar.

- **Contract — os cards.** Sob
  `src/app/perfil/_components/SettingsScreen/components/`, três pastas de três arquivos:
  ```ts
  // CeilingSection — título "Teto de Gastos"
  export interface CeilingSectionProps {
    mode: SettingMode;
    percent: number;          // 0..100
    cents: number;
    maxCents: number | null;  // null = sem período; sem máximo a anunciar
    onModeChange: (mode: SettingMode) => void;
    onPercentChange: (raw: string) => void;
    onCentsChange: (cents: number) => void;
  }

  // GoalsLimitSection — título "Limite em objetivos". Mesma forma exata de props.

  // SimulatedSection — título "Dados simulados"
  export interface SimulatedSectionProps {
    value: boolean;
    onChange: (value: boolean) => void;
  }
  ```
  `CeilingSection` e `GoalsLimitSection` são intencionalmente dois componentes com a mesma
  forma e não um genérico parametrizado: só a copy explicativa difere, e é justamente a copy
  que o R2 e o R3 pedem que seja específica.

- **Contract — `ModeToggle`**, em
  `SettingsScreen/components/ModeToggle/` (irmão dos cards, que é o escopo compartilhado
  mais próximo dos dois consumidores):
  ```ts
  export interface ModeToggleProps {
    name: string;   // nome do grupo de radio; dois na mesma página brigam por um nome só
    legend: string;
    value: SettingMode;
    onChange: (mode: SettingMode) => void;
  }
  ```
  Rótulos: `percent` → `"Porcentagem"`, `fixed` → `"Valor fixo"`.

- **Chose um `ModeToggle` local over promover um `SegmentedControl` para
  `src/components/`** — já existem três cópias privadas (`CapSelector`, `TypeToggle`,
  `KindToggle`), e a do `CapSelector` morre no `260825-1125`. Promover exigiria uma story
  `.mdx` de Foundations e reescrever as outras duas; um quarto uso local resolve os dois
  cards de agora.

- **Contract — `SettingsScreen/percent.helper.ts`.** `clampPercent(raw: string): number` —
  descarta tudo que não é dígito, converte, satura em `0..100`. É onde o "não passa de 100"
  do R2/R3 vive, num lugar só, testável sem renderizar nada. O clamp de centavos é
  `Math.min(cents, maxCents ?? MAX_CENTS)` dentro de `onCentsChange`.

- **Chose travar no clamp do setter over `aria-invalid` + mensagem** — a resposta do dono
  foi "trava no máximo": digitar acima simplesmente não avança o valor, e o máximo aparece
  como texto de apoio no card.

- **Flow — a copy dos cards descreve o comportamento que só chega no `260825-1125`.** O
  card do teto explica porcentagem × valor fixo, e o de objetivos explica que o número
  define o ritmo dos objetivos no dashboard. Ao fim deste prompt o dashboard ainda usa o
  seletor próprio e o `PACE_DIVISOR` fixo, então a copy fica adiantada por um PR. É
  deliberado: escrevê-la duas vezes é pior que ficar um PR à frente.

- **Chose remover `SpendingGoalSection` over mantê-lo ao lado do card novo** — "Meta mensal"
  é literalmente o modo **Valor fixo** do teto: mesma coluna (`ceilingCents`), mesmo
  significado (limite duro do mês em centavos). Dois cards escrevendo a mesma coluna com
  nomes diferentes é o bug esperando para acontecer.

## Forbidden
- Não faça cada card novo buscar e salvar por conta própria: o `PUT` é tudo-ou-nada e três
  gravações concorrentes se sobrescrevem.
- Não use `name` constante no `ModeToggle`: são dois grupos de radio na mesma página.
- Não toque em `CapSelector`, `SimulationSelect`, `simulation.hook.ts`, `pace.helper.ts` nem
  no cálculo em `src/app/api/dashboard/` — o dashboard tem que continuar exatamente como
  está ao fim deste prompt.
- Não promova um segmented control para `src/components/` (exigiria story de Foundations),
  nem acrescente um braço novo a `FieldProps`.
- Não crie um `PATCH /api/settings` nem endpoint por campo.
- Não use `startsWith` em `isActiveNav`, e não crie sub-rota sob `/perfil` (o nav não
  acenderia).
- Nenhuma cor, espaço, raio, sombra ou duração hardcoded nos `.scss` novos — só
  `var(--token)`, com `@use "theme" as t;`.
- Não deixe de mover os testes junto com a pasta: a convenção é `tests/` irmão no mesmo
  diretório do código.
